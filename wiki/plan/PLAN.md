## 一、「仓库」与「美术史」的分界在哪

### 1.1 已经在起作用的机制

不是从零开始。本库有五套机制**确实在工作**,且有数据支撑:

| 机制 | 证据 |
|---|---|
| `DATING_BASIS` 十档 + `DATING_CONF` 四档,且强制「风格比对不得判确证」 | 确证仅占 19.7%,远低于 50% 报警线。这是全库最健康的一项 |
| `VERIFICATION` 三档必填、无「未标」逃生口 | 3,750 条全部有值,memory 仅 256 条 |
| `DEPTH` 两级,且 schema 对 record 豁免 disputes / 单源 / 同名去重 | 两种体裁分得干净,`RECORD_SECTIONS` 只要 basics |
| 「图示级」自动标记(<1000px) | 自动而非靠记得,做法正确 |
| `canon.json` 17 期各带 `anonymity` 与 `dispute` | **这是全库唯一真正「美术史形状」的结构**——它记的是对这个学科的判断,不是对物件的记录 |

### 1.2 还不够的地方,以及为什么

**(a) 深度只在详情页可见,列表页一处没做。** 已实测:

- `render.card_work()` / `card_artist()` **不输出任何深度标记**——图录与分期页里,
  一条克利夫兰照录的著录级条目与一条手写四千字的完整级条目**外观完全一样**;
- `dist/index.html`、`dist/about.html`、`dist/catalog/works.html` 里
  「著录级」三个字出现次数是 **0、0、0**;
- 首页统计条走 `Corpus.stats()`,只给「作品 2,482」一个数,不含深度维度;
- `page_about()` 的十条编纂方针里**没有一条讲深度**。

`audit.depth_mix()` 的文档字符串写着:「若不把比例摊在明面上,『本库每条断言都带认知标注』
这句话就会从事实变成广告。」**这句话是对的,而它只在详情页被执行了。**
读者浏览的地方——首页、图录、分期页——现在呈现的正是一份 2,482 件无差别的藏品名录。

**(b) 没有分母——但有一份已经在库里、从未被当分母用过。** 这是本次最要紧的发现之一,
单列在 1.3。先说结论:全部十三项 audit 检查都是**内省式**的,查这一条对不对;
唯一被当作外部参照的是 `canon.json` 的 17 期,而这个格子太粗——
`audit.scope()` 报「**十七期全部有条目——本库在时间上已无空缺**」,
与此同时器物/石刻/窟寺/雕塑四组的国内来源是 2 件。
**分母粗到报不出偏斜时,它会给出「已无空缺」这种反向误导。**

README 里写过「一份数据可以完全合规而依然很差」。那句话的下一层是:
**一份数据可以每一条都合规、每一条都核实过,而整体是错的东西。** 这一层没有被实现。

**(c) 来源结构没有任何约束。** schema 保证每条为真,没有任何东西保证语料整体的形状。

**(d) 增长只发生在一个轴上。** 按 git 历史:作品 184 → 2,482(**×13.5**);
同期画论 19、事件 21、遗址 37 基本未动,类目 71(一次性补齐)。
**这个曲线不是内容计划的曲线,是 API 可得性的曲线。**

### 1.3 一份已经在库里、从未被当分母用过的清单

`canon.json` 的 `note` 自己写着:「不是本库自创,取自通行中国美术史教材的章节划分
(见 sources.json 中标 spine:true 者),并与英文通史交叉核对」。
也就是说——**本库早就有一份教材来源的权威参照,而且它比 17 期细得多。**
每一期都带 `keys`(5–8 个关键词)与 `centres`(4–6 个中心),合计:

> **`keys` 109 项 · `centres` 89 项 · 共 198 项本库自己声明的核心项**

本次做了一次对账。判据取「**有没有一个以它为题的条目**」,
不是「有没有被某条目提到」——因为缺口检查要的是实体,不是提及:

| | 声明项 | 名称能对上本库某条目的 | 缺 |
|---|---|---|---|
| `keys` | 109 | **22(20%)** | 87 |
| `centres` | 89 | **33(37%)** | 56 |

> **这个比值是粗匹配得出的下限,须人工复核**,原因有三:
> 部分 `keys` 是概念,可能已由名称不同的 `class` 条目承担(如「六法」或落在《古画品录》里);
> 部分是组合名而非实体(「元四家」「北宋三家」);
> 部分 `centres` 是城市而非遗址(「北京」「苏州」「巴黎」),本来就不该立 `site` 条目。
> 所以真实缺口比 87/56 小。**但即按最宽松的折算,缺口仍在半数以上**,
> 且其中有一批毫无争议是缺的:

- **`keys`**:甲骨文 · 妇好墓 · 块范法 · 列鼎制度 · 汉碑 · 瓦当 · 铜镜 · 唐三彩 ·
  汝窑官窑 · 青花五彩 · 宣德炉 · 明式家具 · **版画**(`WORK_KIND_GROUP` 刚为它补了 kind,
  却还没有一个类目条目)· 海派 · 岭南画派 · 月份牌 · 木刻运动 · 八五新潮 · 实验水墨
- **`centres`**:偃师二里头 · 郑州商城 · **安阳殷墟** · 广汉三星堆 · 盘龙城 · 岐山周原 ·
  洛阳成周 · 临淄 · 中山国(平山)· 响堂山 · 巩义 · 汝州 · 芮城永乐宫

**这件事的意义大于它的数字。** 它说明:
1. **分母不必等外部清单**——库里现成就有一份,来源是通行教材,与用户要的「权威参照」同质;
2. `audit.scope()` 只用了 `canon.json` 的 17 期,**把同一个文件里更细的 198 项整个跳过了**。
   一份权威参照摆在 `data/` 里两天没被当参照用,这正是「没有信息收集整理」的最内层形态——
   **不是没有资料,是没有把资料立成判据**;
3. 它给出的缺口方向与 API 可得性**正相反**:缺的是殷墟、周原、三星堆、汉碑、瓦当、
   汝窑、明式家具、木刻运动——**几乎全在国内,几乎全无西方馆藏可摄入**。
   这从另一侧证明了第五节那条配平规则的必要性:**按清单补,自然就补到国内去了。**

所以第六节把这一项排在**核 outline 之前**:它零依赖、今天就能跑、且不受 4.0 那个陷阱影响
(`canon.json` 的权威性来自教材,不来自模型记忆)。

### 1.4 可判定的标准

一部库要能说自己是美术史而非名录,必须同时满足下面四条。**四条全部可由工具判定**,
不靠自评。

> **判据一(有分母)。** 每一个「门类 × 分期」格子上,存在一份外部权威清单声明此格该有哪些;
> 清单条目可追到一份可引用的书目(登记在 `data/sources.json`)。
> 覆盖率 = 已立完整级条目 / 清单必备条目,**能算出一个数**。
> · 判定:`gap.py` 能打印这个数。
> · 现状:**并非「不可计算」——`canon.json` 的 198 项(见 1.3)今天就能算,
>   算出来是 keys 20% / centres 37%(粗匹配下限)。缺的是把它立成判据,不是缺资料。**
>
> **判据二(完整级覆盖正典)。** 清单里标为「必备/正典级」的条目,100% 为 `depth: full`。
> 著录级不得占据正典位。
> · 判定:`gap.py check` 退出码为 0。**现在不可判定。**
>
> **判据三(门类与来源不由 API 决定)。** `WORK_KIND_GROUP` 五组各自的
> 非西方馆来源占比不低于阈值(见第五节),且任一组内单馆占比不超过 60%。
> · 判定:`audit.source_balance()` 全绿。**现在器物/石刻/窟寺/雕塑四组不达标(国内来源 2 件)。**
>
> **判据四(深度对读者可见)。** 每张卡片带深度徽标;首页与图录给出完整级绝对数与占比;
> 编纂方针里有一条讲深度。
> · 判定:`grep -c 著录级 dist/index.html dist/catalog/*.html` 全部 > 0。**现在全部为 0。**

再加一条**否决式判据**,它比上面四条更锋利,也更容易执行:

> **判据五(反事实测试)。把全部著录级条目拿掉再构建一次。
> 剩下的那部站点,就是这部库真正做过判断的部分。**
>
> **这一条本文档写作期间已被实现并提交**(`5e78d47`),而且已经跑出了数:
>
> ```

## 二、3,278 条著录级条目怎么办

**先修正题面:不是 2,288 条,是 3,278 条**——2,288 件作品 + **990 位艺术家**。
prompt 只算了作品那一半。`audit.sourcing()` 报的正是「著录级条目按其性质只引馆方一个源,已豁免单源检查」。
而艺术家那 990 条的页面缺陷更重(见附录 A 第 3 号)。

### 2.1 三个选项的后果

**(a) 全部保留在原位。**
后果:首页继续显示「作品 2,482」,图录继续是 2,482 张无差别卡片,而其中 92% 没有任何人
读过材料。这不是「保留现状」,是**保留一处已经查实的自欺**(1.2 (a))。
且随摄入继续,完整级占比会从 7.8% 单调下滑,那句「本库每条断言都带认知标注」会越来越假。

**(b) 大幅删除,只留能挂到权威清单上的。**
后果:删掉的是**真数据,而且核查等级比本库任何手写条目都高**——2,135 条
`verification=museum`,经馆方 API 逐条核实;而 256 条 memory 全在手写那一侧。
删除还会破坏三处已在依赖它们的机制:`ingest.py` 的藏品号去重(`existing()` / `base_acc()`)、
`recheck.py` 的 `API_MUSEUMS` 白名单判定、`eagle.py` 的本机图库比对。
另外会产生大量死链(现有 60,313 条内部链接)。
**用「看起来更像美术史」去换掉核实过的真记录,是把诚实换成体面。**

**(c) 保留但改变位置。**
后果:内容一条不丢,而「它是什么」在读者第一眼就能看到。代价是要动 build/render 与首页统计,
且要重新定义 `depth_mix()` 的分母(见第六节第 2 步)。

### 2.2 建议:(c),并说清 (c) 具体是什么

**(c) 不是「加个标签」,是七件具体的事:**

1. `catalog/works.html` 与分期页的「作品」网格**只放 `depth: full`**;
   每格末尾加一行「另有本期著录级 N 件,见馆藏索引」。
2. 新增 `catalog/holdings.html`,按 **馆 × 门类** 分页(每页 ≤ 200 条),
   2,288 条著录级作品全部进这里。
3. **艺术家那 990 条同样处理,别只做作品。**
   `catalog/artists.html` 现在是 474,738 B / 1,120 张卡,其中 88% 是 Wikidata 摄入的
   记录级人名——单这一页就已经是一份名录而非美术史。
   完整级 130 位留在图录,990 位进 `catalog/artists-index.html`。
   **这一条最容易被漏掉,因为「著录级」在讨论里几乎总被默认成「作品」。**
4. **著录级条目保留独立页面,URL 不变。** 这一条是硬要求——
   3,278 个页面已被 60,313 条内部链接引用,改 URL 等于自造一场断链事故,
   而 `build.check_output()` 会把它拦成构建失败(这是好事,但不必去撞)。
5. `card_work` / `card_artist` 一律输出深度徽标。
6. 首页统计改为**两个数不给合计**:
   「作品 · 完整级 194 / 著录级 2,288」「艺术家 · 完整级 130 / 著录级 990」。
7. `page_about()` 的编纂方针加第十一条,讲两级深度是两种体裁。

**理由三条:**

- **删不得**,见 2.1(b):它们是本库核查等级最高的一批数据,且已被三处机制依赖。
- **留在原位不行**,见 1.2(a):位置本身在做断言。一条进了正文图录的条目,
  就是在宣称它经过了正文那套审查。
- **「不删内容、但让它的地位在页面上可见」是本库已经用过两次的手法**:
  `no-free-image` 与 `copyright` 的分别(一个断言已公版、一个断言仍在保护期)、
  「图示级」自动标记(600px 认得出是哪件、不足以论笔墨)。
  (c) 是同一手法的第三次应用,**与既有立场一致,不需要发明新原则**。

### 2.3 顺带必做的两件清理(小,但属同一议题)

- **168 条缩略图仍是外链未落盘。** L10 立的规则是「每条外部引用都要有一个只有真做过
  才会存在的副产品」;外链绕开了那个副产品——`schema._check_image` 只对 `img/…` 查文件存在,
  对 `https://` 直接放行。要么落盘,要么整块删掉。
- **843 个孤儿图**(202 MB 里的一部分)。批次已收工,该清了。

## 三、10 万这个目标该不该接

**建议:不接 10 万作为条目数目标;接它作为「馆藏索引覆盖」目标,并把目标改成三层。**

### 3.1 可得量是真的,成分不是

见 0.5。三条已核的事实,合起来足以判定:

- 国博的 26.8 万 ≈ 国博自报藏品总数 25.15 万 → 那是**库房清册**,含钱币、图书、革命文物、标本;
- 故宫的 12.8 万里 7.5 万条只标到「艺术作品」,判不出门类 → 撞上 `ingest.py`
  的第一原则「判不出来就不摄入」;
- **台北故宫只有 1,285 条,已抽走 11.7%** → 书画正典这一路余量已经用完。

**所以结论不是「10 万里含杂质」,而是「10 万几乎全是库房清册,正典余量已经用完」。
加到 10 万,加的不是美术史,恰恰是仓库。** 用户提 10 万的理由是
「这样你就不会只找海外的了」——**这个理由完全正确,但 10 万不是它的解法**:
总量上去了偏斜可以一点不变(现在 83.4% : 8.8%,而国内那 8.8% 里 95% 是书画)。
偏斜要用第五节的配平硬规则解,不用总量解。

### 3.2 技术上限:两处硬墙,不是线性放大

以 0.4 的实测单位成本推算 10 万件(**以下标「推算」者均为推算,依据即 0.4 的均值**):

| 项 | 现状(实测) | 10 万件(推算) | 性质 |
|---|---|---|---|
| `data/works/` JSON | 12 MB | **261 MB**,单目录 10 万文件 | 可承受但难看 |
| `dist/works/` HTML | 22 MB | **587 MB** | 可承受 |
| **`catalog/works.html`** | **1,002,167 B** | **约 40 MB 的单个 HTML** | **硬墙:浏览器打不开** |
| **`search.json`** | **582,535 B** | **约 15.8 MB,每访客首屏必下** | **硬墙** |
| build 耗时 | 72 秒 | **≥ 32 分钟** | 见下,这是下限 |
| `static/img` 全量复制 | 202 MB / 次 | 若各配一图约 **13 GB / 次** | 独立瓶颈 |

**build 耗时那一行必须说清是下限而非估计,理由是代码里有一个超线性项:**

`build.page_artist()` 每页调 `Corpus.works_of(aid)`,而 `works_of` **全表扫描 `self.works`**。
复杂度是 O(艺术家 × 作品):现在 1,120 × 2,482 ≈ **278 万次**;
2,000 艺术家 × 10 万作品 ≈ **2 亿次**,增长 71 倍,而页数只增 27 倍。
`works_at()`、`children_of()`、`page_period()` 同为全表扫描。
另有 `check_output()`:现在 60,313 条链接、每条一次 `Path.resolve().exists()`;
10 万页按同比例约 **160 万次** 文件系统调用,外加把 587 MB 的 HTML 重新读一遍。
**所以「72 秒 × 27 倍 ≈ 32 分钟」是线性下限,真实值必然更差。**

**git 与 Windows 文件系统:** NTFS 单目录 10 万文件功能上可以,`git` 也能装。
但两件事会坏:
- **`git status` / `add` / `checkout` 在 Windows 上退化到分钟级**(Windows 的 lstat 成本远高于 Linux)。
  现在工作区已有 1,411 个未提交改动,已经能感觉到。
- **更严重的是 commit 的可读性**:每次摄入批次产生上万个新文件,
  **diff 审阅不了的版本控制等于没有版本控制**。这比性能问题严重。

若真要走 10 万,需要**四到六项动核心的架构改动**:
data 分片目录(`data/works/<hash 前二位>/`)、**著录级不单独出页(只进分页索引与一份 JSONL)**、
图录分页 + 分面、`search.json` 分片或前缀索引、增量构建(要求先把全表扫描换成预建反向索引)、
`check_output()` 改缓存 + 只查新页。每一项都动 build/render 的核心。

### 3.3 更要紧的那一问

**10 万条著录级 + 194 条完整级是什么东西?**
答:**一个搜索引擎,不是一部美术史。** 完整级占比从 7.8% 掉到 **0.19%**。
`audit.depth_mix()` 现在就在报警「完整级仅占 7%」;10 万会把它变成两位小数。

### 3.4 建议:改成三层目标

**保留 10 万这个数字,但重新指派它属于哪一层。**

| 层 | 内容 | 目标量 | 是不是「条目」 |
|---|---|---|---|
| **一 · 正典完整级** | 全部 `depth: full`,全部挂在权威清单的「必备」位上 | 作品 **600–900** · 艺术家 **≥202**(名单全覆盖,含缓冲取 250)· 遗址 **≥52** · 类目 **≥150** · 画论 **≥24** | 是,这是正文 |
| **二 · 著录级条目** | 只收能挂到第一层清单上的(某正典画家的其他存世作品、某窑口的其他标本) | 作品 **上限 5,000** | 是,但进「馆藏索引」不进正文图录 |
| **三 · 馆藏索引** | `data/index/holdings-*.jsonl`,每行一条馆藏记录(QID、题名、馆、藏品号、URL) | **不设上限,10 万甚至 57 万** | **不是。** 不出条目页、不进图录、不计入「作品」数 |

- 第一层的数量级依据(已按四份 outline 校准):
  `artists-outline.json` 的 **202 位一级名单**(本库已完整级 131 位,**缺 71 位**)、
  `plan/sites-outline.json` 的 **52 处遗址**(本库 37 处)、
  `plan/canon-chain.json` 的 **24 环著录链**(本库已立 treatise 10、仅登记 source 9、完全空白 5)、
  `plan/coverage-outline.json` 的 32 个卷目(《中国美术全集》一系的卷次体量),
  以及 `canon.json` 的 **198 项 keys/centres**(见 1.3)。
  **作品的 600–900 仍是推算**:它由 coverage-outline 的「数量级估计」加总而来,
  而那些估计的确信度多为「记得」,按 4.5 规则丙**不得用作配额值**——
  所以这个数在第 5 步核完 coverage-outline 之前只是量级参考,不是目标。
- 第二层的 5,000 依据(推算):5,000 件时 `catalog` 约 2 MB(需分页)、
  `search.json` 约 1 MB、build 约 3–4 分钟——都在**修补范围内,不需要架构改动**。
  这就是「不改架构能承受的上限」。
- **第三层才是用户那句「不会只找海外的了」真正的落点**:国内馆那 57 万条库房记录
  一件不落地进这一层,而且它顺带成为第四节算缺口的对账底表。
  10 万这个数字在这一层是合理的,在第一层是荒谬的。

**一句话结论:10 万——部分接,接在第三层;第一层要的是 600–900,不是 10 万。**

## 四、权威参照到手后,覆盖清单怎么变成可执行的排查

### 4.0 先说一件比工具更要紧的事

`plan/` 下四份 outline 已全部落地(`coverage-outline.json` 32 条、`canon-chain.json` 24 条、
`sites-outline.json` 52 条、`artists-outline.json` **202 条**)。我读过它们的结构与自述。
**它们自己写着:**

> 「本文件不是核过的书目,是从记忆与少量 WebFetch 核对整理出的排查用清单……
> 按本库 sources.json 信源分级**仅为第 4 级二手转引强度**」
> —— `coverage-outline.json` 的 `note` 与 `confidence_levels`

`canon-chain.json` 的确信度分布是 **确知 13 / 记得 6 / 待核 15**。

**这一点是本次分析里最要紧的判断:如果拿「记得/待核」的清单当分母,
本库会按一份模型记忆产出的书目去造条目——那是把「按 API 可得性填」
换成「按记忆可得性填」,而且更坏,因为后者看起来更像权威。**
这正是 L10 那类错误的新形态:**不是编造出处,是编造缺口。**

所以据以推进的**第一步是核它,不是用它**(第六节第 5 步)。

### 4.1 第三把尺子已经开工了 —— 扩 `gap.py`,不扩 `audit.py`

**本文档写作期间,另一路已把 `gap.py` 落到仓库根目录并提交**
(`30819e5 feat(缺口): 新增 gap.py, 第一次能列出「论述在而被论述者不在」`),
现有三个子命令:`artists` / `orphan-artist` / `outline`。
本节因此不是「提议新建」,是**给一个已存在的工具补设计**。先确认它的定位是对的:

README 已立两把尺子的分工:`schema.py` 查结构、`audit.py` 查内容像不像话。
**gap 查的是第三类东西:该有而没有。** 前两把都是内省式,gap 是外部对账,
输入不在 `data/` 里。混进 audit 会让 audit 的「只报告不拦构建」承诺变得含糊
(gap 的一档是要拦的)。**故单独立第三把是对的,位置也对**
(它要读 `plan/*-outline.json`,又要读 `data/`,放根目录与 `audit.py` 同级最顺)。

它已经做对了一件要紧的事,值得记下来:**方向是「拿名单比对文本」,
而不是「从文本发现名字」。** 它的文档字符串记着第一版走反了——
从正文提取 2–4 字汉字串当人名候选,6,290 项里前几十全是本库自己的套语
(「现藏」「本库不作」),那正是 L11 的宽模式认结构。**能穷举的一侧当白名单。**

本节要补的是三处:4.2 的归一化契约、4.3 的两类需求分流、
**4.5 的入队规则(它现行那一条会产出空队列,必须改)**。

### 4.2 输入契约(按已落地的真实形状写,不是猜的)

四份 outline **形状互不相同**,键全是中文,链接字段各叫各的:

| 文件 | 顶层形状 | 每条的键 |
|---|---|---|
| `coverage-outline.json` | `{schema, note, confidence_levels, items:[...]}` | `id / 编 / 系列 / 卷 / 门类 / 时代范围 / 本库对应分期 / 本库对应kind / 数量级估计 / 确信度 / 依据` |
| `canon-chain.json` | `{schema, note, confirmed_via_webfetch, items:[...], 统计}` | `书名 / 作者 / 成书 / 体例 / 收人数 / 收件数 / 确信度 / 本库条目` |
| `sites-outline.json` | **裸 list** | `名称 / 地点 / 年代 / 性质 / 有正式报告 / 批次或名录 / 确信度 / 本库条目 / 建议层级` |
| `artists-outline.json` | **裸 list** | `姓名 / 生卒 / 门类 / 分期 / 级别 / 依据 / 确信度 / 本库条目 / 现状` |

`artists-outline.json` 的实测分布(202 条):
确信度 确知 126 / 记得 54 / 待核 22;现状 curated 131 / **缺失 47** / **record-stub 24**;
分期 清 47、晚清民国 25、隋唐 23、明 22、魏晋 17、北宋 16……
`本库条目` 字段指到真实 id 的 131 条**全部已是完整级**。
→ **一级名单的缺口是 71 位(47 完全缺失 + 24 只有 record-stub)。**

两处要回给该文件作者的问题(**我不改它,只记下来**):
① `级别` 字段 202 条**全为「一」**,字段存在但无区分力,不能用作「必备/正典级」的筛选键;
② 131 条 `本库条目` 指向的实际只有 130 个完整级艺术家 → **清单里有一处重复指向**,须去重。

所以 gap.py 第一件事是**归一化**:一个 outline 一个 loader,输出统一记录

```
Demand = {src_file, src_id, entity_kind, label, kind_hint, period_hint,
          demand_type, want_depth, quota, confidence, evidence}
```

### 4.3 最要紧的一个设计决定:清单有两种,不能混

- **点名式(`demand_type="named"`)**:清单直接点出一个具体对象
  (《历代名画记》、半坡遗址)。对账方式是**匹配**——按名称/别名找本库条目;
  有→查 depth 够不够;无→出一条缺口。
- **配额式(`demand_type="quota"`)**:清单只说这一格该有多少
  (《中国美术全集·绘画编·卷轴画》五卷,数量级估计 500)。对账方式是**计数**——
  数本库该格的完整级条目数,与配额比,出差额。

**把配额式硬拆成点名式会立刻制造几百条编造的待办。** 这是 4.0 那个陷阱的具体形态,
必须在数据结构层面分开,不能靠使用者自觉。

### 4.4 输出:在现有三个子命令之外再加三个

```bash
# 已存在
python gap.py artists                     # 名单 × 本库条目 × 本库正文
python gap.py orphan-artist               # 完整级作品 artist 为空而可补者
python gap.py outline                     # 与 plan/*-outline.json 对账
# 本规划要加
python gap.py canon                       # canon.json 的 198 项 keys/centres 对账(第 3 步)
python gap.py census                      # 只统计,不判定
python gap.py queue [--period X] [--kind Y] [--out plan/gap-queue.json]
python gap.py check                       # 门禁,ERROR>0 则退出码 1
```

**`canon`** —— 1.3 那份库内清单的对账。零依赖,不读任何 outline。

**`census`** —— 各 outline 载入了多少条需求、确知/记得/待核各多少、
`依据` 能否解析到已登记的 src id、**规则乙四种互证各命中多少**、能对上本库的多少。
**这一步必须先跑**,因为它输出的第一个数就是「这份分母有多少能用」。

**`queue`** —— 优先队列。排序键依次:
① **入队资格按 4.5 规则乙的四种互证判,不按确信度判**
  (确信度只决定它进哪一档待核,不决定要不要做);
② `entity_kind` 权重:`treatise` / `site` / `class` **高于** `work`
  (骨架条目不需要图版、不受馆方 API 限制、多在国内文献里,
  是判据三唯一能立刻改善的方向);
③ 已有 `record-stub` 者优先于完全缺失者(壳已在,是升级不是新建——
  `artists-outline` 里这类有 24 位);
④ 分期缺口占比大者先;⑤ 门类缺口占比大者先。
输出 `plan/gap-queue.json`,每条带**「凭哪一条互证入队」**的可读理由。

**`check`** —— 门禁档,只查一件事:
**已入队且互证等级最高的那一档**(规则乙①或②命中)对应的本库条目
不存在或不是 `full` → ERROR。**这一档才能进 CI。**
注意 `check` 的判据是互证,不是确信度——**用确信度做判据它会永远返回 0**(见 4.5)。

### 4.5 硬规则,以及一个必须纠正的门禁

初稿我写的规则是:「只有 `确信度 == 确知` 且 `依据` 已登记进 `sources.json` 的需求,
才能生成缺口工单。」**已落地的 `gap.py` 文档字符串里也有一条同类的:
「清单自身标『待核』的条目不能当基准用」。两条都要改,而且不是微调。**

**一次对账就足以判定。** `artists-outline.json` 202 位一级名单对本库实测:

| 确信度 | 名单人数 | 本库已有 | **缺** |
|---|---|---|---|
| 确知 | 126 | **126** | **0** |
| 记得 | 54 | 5 | **49** |
| 待核 | 22 | 0 | **22** |
| 合计 | 202 | 131 | **71** |

> **确信度为「确知」的 126 位,一位不缺。缺的 71 位,全部是「记得」或「待核」。**
>
> **所以「确信度=确知」这个门禁产出的队列长度恰好是 0。** 它不是偏严,是完全失效。
> 而 `gap.py` 现行的「排除待核」这一档,会排掉 22 位:
> **曹不兴、曹仲达、杨子华、李昭道、周臣、林良、吕纪、禹之鼎、改琦、费丹旭、皇象……**
> 其中 **曹仲达就是「曹衣出水」的那个曹**,而「曹衣出水」四字**写在 `canon.json`
> 隋唐一期的 `dispute` 里**;杨子华在同期;李昭道是小李将军。
> 这些人被门禁挡在队列外,而挡他们的理由是「生卒年待核」——**生卒待核正是他们的史实状况。**

原因是:**`确信度` 标的是「这条依据文字有多可靠」,不是「这个人该不该在库里」。**
名单作者把它挂在生卒与依据描述上是对的;拿它当收录门禁则是张冠李戴。
`artists-outline` 的 `确信度` 挂在生卒与依据描述上;
`coverage-outline` 的挂在「该卷是否存在及其规模」上;
`canon-chain` 的挂在「收人数/收件数」这些数字上。**三份清单的确信度说的不是同一件事。**

修正后的规则:

> **规则甲(确信度只管它自己声明的那类事实)。**
> `确信度` 门禁只作用于该 outline 声明的那一类事实——数字、规模、生卒、卷次。
> 它**不作用于**「此人/此书/此地该不该在库里」这一类需求。
>
> **规则乙(该不该在库里,用互证判,不用确信度判)。**
> 一条点名式需求可入队,需满足下列**任一**互证:
> ① 该名称出现在 `canon.json` 的 `keys` / `centres` / `anonymity` / `dispute` 里,
>    **或出现在其中某个组合名所指的人之列**(本库自己的教材来源骨架已承认它是正典);
> ② `依据` 能解析为一个已登记在 `data/sources.json` 的 src id;
> ③ 两份以上 outline 独立点到同一个对象;
> ④ 该名称出现在本库某条**完整级**条目的正文里
>    ——即 `gap.py` 已在做的那件事:「论述在而被论述者不在」。
> 四条都不满足 → 只进 `census` 的待核清单,不入队。
>
> **①里那个「或」不是可以省的,而它也不能自动做。** 实测:71 位缺失者中
> **姓名直接出现在 `canon.json` 里的只有 5 位**(陆探微、张僧繇、谢赫、张彦远、徐熙);
> 但 `canon.json` 里另有一批**组合名**——曹衣出水、吴带当风、黄筌徐熙、荆浩关同、
> 董源巨然、张萱周昉、吴门四家、四僧、扬州八怪、岭南画派、海派、元四家、北宋三家——
> **每一个都指着若干具体的人,而那些人正落在缺口里。**
> 展开这批组合名需要一份人工写的映射(`plan/canon-groups.json`),
> **这是必须做的手工活,不能靠字符串匹配变出来**——
> 而 `canon.json` 各期的 `dispute` 已经反复警告过这类组合名是后世归拢
> (「北宋三家并非一个名单而是两个」),所以映射本身就要并列异说,不能压平成一份。
>
> **规则丙(数字一律不入正文)。**
> 凡 `确信度 != 确知` 的**数字**(收人数、收件数、数量级估计)不得写入任何条目,
> 也不得用作配额式需求的配额值——配额缺依据时,该格只报「未定额」,不报差额。
>
> **规则丁(不满足互证的需求,优先级最高的工作是去核,不是去填)。**

规则乙是这份规划里最关键的一处修正,理由:
**初稿那条规则(以及 `gap.py` 现行那条)本身就是 4.0 那个陷阱的镜像。**
4.0 防的是「拿记忆当权威去填」;而这条门禁的毛病是「拿记忆的不确定去否决真正的正典」——
**同一个错误的两个方向,都是把「确信度」当成了它不是的东西。**
一个把库填成记忆的形状,一个把库缩成记忆有把握的那一小块;
**后者更隐蔽,因为它看起来很严谨,而它的产物是一个空队列。**

规则乙里的 ①④ 把两份**库内**参照接了进来:`canon.json` 的骨架(1.3)
与本库完整级条目的正文。**于是 outline 与本库互为验证者,谁都不必单独充当权威**——
这也正是 `gap.py` 已经做对的那一半(它的 `artists` 与 `orphan-artist` 子命令
就是在做 ④),本规划要补的是 ①②③ 与那份组合名映射。

判定标准:`census` 跑通并报出四份 outline 的确信度分布与四种互证各命中多少;
`check` 给出非零缺口数——**且这个数必须显著大于 0**(现行门禁下它是 0,那就是失效的信号);
**人工抽查 20 条,每条都能说出它凭哪一条互证入队**。

## 五、来源配平的硬规则

### 5.1 现状(实测,重述一遍因为它决定规则形状)

- 全库:西方三馆 2,070(83.4%)· 国内 `wd-` 218(8.8%)· 手写 194(7.8%)
- **国内那 218 件:画作 207 · 书法 9 · 陶瓷 2**
- → **器物组 / 石刻组 / 窟寺组 / 雕塑组的国内馆来源合计 2 件**

**所以按全库总量配平是无效的:** 只要继续摄入国内书画,全库比值会好看,
而器物组仍然 100% 由西方馆藏定义。**规则必须按 `WORK_KIND_GROUP` 的五组分别算。**

### 5.2 建议的硬规则(进 `ingest.py`,与既有强制同级)

本库已有两处先例:`schema.py` 强制「风格比对不得判确证」、
`ingest.py` 强制「判不出就不摄入」。配平也该是这种强制,不是叮嘱。

```
规则一 · 门类配平,按组算不按全库算
  对 WORK_KIND_GROUP 的五组各自算:
    非西方馆占比 = (国内馆 + 原址 + 考古报告来源) / 该组条目总数
  任一组 < 25% 时,拒绝再向该组写入西方馆来源的著录级条目,
  并打印该组当前比值、以及补到阈值所需的国内来源件数。

规则二 · 单馆上限
  任一 source id 在任一组内占比不得 > 60%。
  现状:器物组 cleveland 远超此值 → 该组冻结西方摄入。

规则三 · 不可绕过
  门禁放在 `--apply` 的写盘循环**之前**,不是之后;
  且不提供 --force。要突破只能改常数并在 commit 里说明理由
  ——与 schema 的做法一致。

规则四 · 诚实退路,防「为配平而编造」
  当规则一挡住写入、而国内来源确实取不到时,正确动作是
  **在 data/gaps/ 记一条缺口登记(门类 + 分期 + 为何取不到)**,
  不是降阈值,也不是把西方藏品硬算成国内来源。
```

**阈值 25% 的依据要说清:** 这是「不得低于某值」里最保守的可辩护值。
它不主张「国内应占多数」(那需要一份存世分布的证据,本库没有),
只主张**任一门类不得由西方馆藏单独定义**。
**我明确把 25% 标为待用证据校准的参数**——真正该锚定的是各门类的存世与出土分布
(考古报告、《中国文物地图集》一类)。那份证据到手前,25% 是操作性下限,不是结论。

### 5.3 配套的报告项(不拦,只报)

给 `audit.py` 加 `source_balance()`:按五组打印非西方来源占比与单馆最高占比。
硬规则拦的是新增,**已有的偏斜要靠报告持续可见**——这和 `depth_mix()` 存在的理由相同。

## 七、这次的方法论教训(供 `tasks/lessons.md`)

用户说的是「没有信息收集整理和实施规划」。落成一条可复用的规则:

### 什么情况下应当先建立领域的权威参照,再动手填内容

**满足任一即触发:**

1. **任务是「建一部关于某个已有学科的库/志/史/图谱」** ——
   即该领域自身已经有正典、目录、全集、名录。
   **这类领域的「该有什么」是外部既定的,不是能从数据里发现的。**
2. **内容的可得性在各子领域之间极不均衡**(有 API 的 vs 只有纸本的)。
   不均衡越大,越必须先有分母——否则填充路径会自动选择低阻力方向,
   而这个选择不会报错。
3. **能被一句话否定为「这不是 X」。** 能被外行一句话否定的产出,
   说明它的**形状**错了,不是内容少了。加内容不会修好形状。

### 本库的具体表现

- **没有分母,于是「该有什么」这个问题在整个项目里从未被提出过。**
  所有质量机制——`schema.py` 的必备维度、`audit.py` 的十三项自检——都是**内省式**的:
  查「这一条对不对」,查不了「该有的在不在」。
  README 写过「一份数据可以完全合规而依然很差」;它的下一层是
  **「一份数据可以每一条都合规、每一条都核实过,而整体是错的东西」**,而那一层没实现。
- **唯一的外部分母 `canon.json` 17 期格子太粗**,以致 `audit.scope()` 报
  「**十七期全部有条目——本库在时间上已无空缺**」,
  同时器物/石刻/窟寺/雕塑四组的国内来源是 2 件。
  **分母粗到报不出偏斜时,它给出的是反向误导。**
- **于是填充按可得性排序,库的形状 = 开放数据计划的形状:**
  克利夫兰完整 CC0 API → 1,580 件(63.7%);芝加哥无需 key → 460 件;
  大都会须过滤产地 → 30 件;国内馆无 API → 218 件且 95% 是书画。
  **这个分布精确复现了 MUSEUMS.md 那张可得性表的排序,与中国美术史的门类分布无关。**
- **信源表里早就登记了该找谁,一条没引:** 112 条信源中 27 条从未被引用,
  其中 15 条恰是国内机构与中文原典(10 家博物馆/考古院所 + 《宝章待访录》《书史》
  《宋史》《画鉴》《新唐书》,全为 tier=1)。**不是不知道,是路径没往那边走。**
- **最刺眼的一层:本库有几十条条目在讲这个不对称。**
  README 有专节;`ingest_cn.py` 的文档字符串写着「若作品九成来自西方馆,
  本库就是『西方馆中国藏品目录』冒充中国美术史」。**然后用数据把它重演了一遍。
  写得越清楚,重演越刺眼。**

### 规则条文

> **L12. 建「某领域的库」之前,先取该领域的权威参照(正典/目录/全集/名录),
> 把它做成机器可读的分母;没有分母不要开始填内容。**
>
> **触发条件**:① 领域已有既成正典或目录体系;② 内容可得性在子领域间不均衡;
> ③ 产出能被一句话否定为「这不是 X」。
>
> **为什么**:所有内省式校验(schema / lint / audit)只能保证「每条对」,
> 保证不了「整体是那个东西」。**「该有什么」是外部知识,不在数据里,校验器发明不出来。**
>
> **先做三件事**:① 取权威清单并落成机器可读;② 算出「该有而没有」的缺口;
> ③ **给缺口按分期/门类排优先级,让填充顺序由清单决定,而不是由 API 可得性决定。**
>
> **反向陷阱(本次的新发现)**:补权威参照时若用模型记忆生成清单,
> 是把「按 API 可得性填」换成「按记忆可得性填」,**更坏——后者看起来更像权威**。
> 所以清单条目必须自带确信度,且**只有能追到可引用书目的那部分才可用作分母**。
> (本例四份 outline 自述为第 4 级二手转引强度;`canon-chain.json`
> 确信度分布为 确知 13 / 记得 6 / 待核 15。)
>
> **与既有教训的关系**:L1 是「改动前建立**事实**基线」(查这个项目的历史);
> L12 是「填内容前建立**领域**基线」(查这个学科的正典)。
> **L1 防重造轮子,L12 防造错东西。**
> 与 L10 同源:L10 是「编造的出处」,L12 的反向陷阱是「编造的缺口」——
> 都源于「凭记忆产出的东西与核实过的东西在文件里长得一模一样」。

## 附录 A · 本次通读代码与数据时查实的四个缺陷

均已实测确认,不是推测。列在这里供第 1 步直接执行。

**A1 · 列表页不标深度(判据四不达标的直接原因)**
`render.card_work()`(render.py:371)与 `card_artist()` 不输出任何深度信息。
后果:`catalog/works.html` 的 2,482 张卡、17 个分期页的作品网格里,
著录级与完整级外观完全一样。且 `dist/index.html`、`dist/about.html`、
`dist/catalog/works.html` 中「著录级」出现次数为 0、0、0。
**「深度是一等字段并在页面上明示」目前只在详情页成立,列表页一处没做。**

**A2 · 2,288 个页面显示字面 `**`**
`render.inline()`(render.py:52)有 `re.sub(r"\*\*([^*]+)\*\*", r"<b>\1</b>", s)`,
但 `build.page_work()` 的著录级横幅是硬编码 HTML 字符串,**绕过了 `inline()`**。
实测:`grep -l '断代依据亦非本库所判\*\*' dist/works/*.html | wc -l` → **2,288**。
数据里的 `**` 没这个问题(走 `inline()`),只有这条硬编码横幅有。

**A3 · 990 个著录级艺术家页的小节标题是原始 id**
`schema._check_sections()` 对 `depth=record` 换用 `RECORD_SECTIONS`(只要 `basics`),
但 `build.page_artist()` 无条件按 `ARTIST_SECTIONS` 渲染,而 `ARTIST_SECTIONS` 里**没有 `basics`**。
于是 `basics` 走 `_sections()` 的「未知小节」分支,标题取原始 id、注解写「本条目自加维度」。
实测 `dist/artists/wd-q1005462.html`:
`<span class="sec-n">basics</span><span class="sec-note">本条目自加维度</span>`。
`page_work()` 有对应处理(`if depth_of(w) == "record": spec = RECORD_SECTIONS`),
`page_artist()` 漏了。

**A4 · `audit.py` 已被自己的输出淹没**
`epistemics()` 不像 `dupes()` / `sourcing()` 那样豁免 `depth=record`,
于是每条著录级条目都触发「全篇无争议也无旧说」与「全篇无空缺也无待校」。
实测:总输出 **3,361 行,其中 [态度] 3,335 行(99.2%)**;
真正需处理的只有 4 条 [未译]。**这把尺子现在读不了,得先修好再用它验收后续步骤。**

**A5(数据卫生,非缺陷但要提)**:218 条 `wd-` 作品里没有独立的藏品号字段,
其中约 170 条把藏品号并入了 `holder`
(如 `国立故宫博物院(台北)藏品号 故畫000054N`),另 47 条 `holder` 干净。
同一字段两种用法,会让按馆聚合的统计(第五节规则一要用)出错。
